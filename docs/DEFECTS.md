## D-1. Деньги неисполненного поручения уходят в RELEASED (высокая)

`POST /escrow/{deal_id}/event` принимает в `type` внутренние события `mandate_signed` и `cleared`
(`app/escrow/router.py`, `Event = Literal[...]`). Для поручения, которое корзина **не исполнила**, эскроу стоит
в `DEPOSIT_HELD`; клиент сам шлёт `cleared` → `MATCHED` (без количества, суммы и завода), затем
`payment_confirmed` → `PAID_IN_FULL`, затем `ettn_signed` → `RELEASED` «деньги переведены заводу».
Сверка накладной пропускается, потому что `qty_t` и `amount` пустые.

Воспроизведение (после `POST /demo/step/2`, `1F66-8B` — неисполненный покупатель сценария):
```
POST /escrow/1F66-8B/event {"type":"cleared"}            → 200 MATCHED
POST /escrow/1F66-8B/event {"type":"payment_confirmed"}  → 200 PAID_IN_FULL
POST /escrow/1F66-8B/event {"type":"ettn_signed"}        → 200 RELEASED, seller=null, amount=null
GET  /mandate/1F66-8B                                     → status "open" (поручение всё ещё ждёт корзину)
```
Почему важно: это ровно тот вопрос, который задаст жюри про «деньги по подписи получателя». На демо кнопками
не воспроизводится (фронт шлёт только `payment_confirmed`/`ettn_*`/`timeout`/`shipped`), но через API — да.

Как чинить (одна строка): убрать `mandate_signed` и `cleared` из `Event` в роутере — их шлёт только сервер
(`escrow/store._from_run`). Дополнительно: `sm.apply(..., "cleared")` без `qty_t`/`amount` → `TransitionError`.

## D-2. Неизвестный или пустой регион принимается (средняя)

`POST /mandate/preview` с `region: "Mars"` или `region: ""` отдаёт `errors: []` и черновик поручения;
`/mandate/sign` его подписывает, поручение лежит в корзине. Движок не находит тарифа → поручение не исполняется
с причиной `price_below_clearing`, и карточка объяснения говорит про цену, хотя дело в регионе.
Пустая строка не считается пропущенным полем (`service.preview` проверяет только `is None`).

Воспроизведение: `POST /mandate/preview {"fields":{..., "region":"Mars"}, "principal":{"kind":"ip","inn":"900000001"}}`
→ 200, `mandate_draft` не null.

Как чинить: в `check_fields` — ошибка `region_unknown`, если `region not in app.regions` (пустая строка — `missing`).

## D-3. Повторная подпись удваивает спрос (средняя)

Один и тот же черновик, отправленный в `/mandate/sign` дважды (двойной клик, повтор запроса после таймаута),
даёт два поручения `ECFF-5D` и `ECFF-5D-2` с одинаковым хешем; спрос корзины 400 т вместо 200 т.

Как чинить: в `book.store.add_mandate` — если хеш уже есть среди открытых поручений, вернуть существующий id
(идемпотентность по хешу), а не создавать `-2`.

## D-4. `mandate_id` из тела запроса (низкая)

`/mandate/sign` с `mandate_id: "FAKE-00"` создаёт поручение `FAKE-00`; id не сверяется с хешем
(`mandate_id_from_hash`). Подпись и хеш верные (id в хеш не входит), поэтому денег это не касается — только
читаемости журналов и «Мои поручения».

Как чинить: в `service.sign` пересчитывать `mandate_id = mandate_id_from_hash(h)`.

## D-5. Технический текст на мусорной накладной (низкая)

`ettn_signed` с `signatures: "four"` → 422 `invalid literal for int() with base 10: 'four'`;
с `qty_t: "abc"` → 422 `Invalid literal for Fraction: 'abc'`. Не 500, но текст не для человека.

Как чинить: в `ettn_event.check` ловить `ValueError` и отвечать «накладная заполнена неверно: …».

## D-6. Ответы фреймворка на английском (низкая, E.6)

| Запрос | Ответ сейчас |
|---|---|
| неизвестный маршрут `GET /nope` | 404 `{"detail":"Not Found"}` |
| невалидный JSON в `POST /intake/parse` | 422 `{"detail":[{"type":"json_invalid","msg":"JSON decode error",...}]}` |
| неверный тип поля (`qty_t: 2.5`, `grade: "30.0"`) | 422 список ошибок pydantic на английском |
| неизвестный `mode` у корзины | 422 `String should match pattern ...` |
| неверная дата в событии эскроу | 422 `Invalid isoformat string: 'вчера'` |

500 нет ни в одном случае. Фронт показывает свою строку по коду ответа, поэтому пользователь английского
не видит; но ментор, открывший `/docs`, увидит. Как чинить: обработчики `RequestValidationError` и 404 в
`main.py` с текстом «запрос заполнен неверно: поле …» / «такого адреса нет».

## Проверено и дефектом не является

- Двойное закрытие корзины — тот же `run_id` и тот же результат.
- Закрытие пустой корзины — 200, цены нет, заводы в `asks_unfilled: no_demand`.
- Закрытая корзина новых поручений не принимает: подпись после закрытия кладёт поручение в следующую.
- Поручение, истекающее до закрытия окна, в корзину не попадает (I14).
- Накладная чужой сделки — 404 с русским текстом, состояние не меняется.
- Повторная накладная после выплаты — 200 `ignored: true`, выплата одна.
- `ettn_rejected` после выплаты — 409 «из RELEASED переходов нет».
- 50 параллельных подписей в одну корзину — 50 разных id, объём сходится до тонны.
- Потолок 1 сум — предупреждение, не запрет (02 §M2); 10⁹ — точные суммы, допуск блокирует по деньгам.
- `10⁹ т × 10¹⁸ сум` — `int` без переполнения.
- `?admin=1` ничего не раскрывает; `mode=admin` — 422.

## Не проверено (нет в master)

Гость без cookie, подделанный cookie, admin без токена — слой доступа (`app/auth`, `app/middleware`) лежит
только в ветке `night-wip` и в master не подключён (в master остались лишь `__pycache__`). Пока он не влит,
режимы `mode=plant|supervisor` открыты без токена; они показывают id поручений, тонны и регионы, но не потолки
(проверено тестом `test_buyer_view_has_no_ceilings`).
